Brix Build Layers

Design note — how incremental, cached, and atomic builds stack on top of a plan that grows while it runs  ·  July 2026

1. What this note is about

A Brix build file describes actions and the files they read and write. From that, Brix figures out the order and runs things. The simplest builder — CleanBuilder, already working in the prototype — just runs everything, every time.

The spec adds three more abilities, and users turn them on by nesting builders: 

AtomicBuilder(                        # nothing lands on disk unless the whole build succeeds
    CacheBuilder(                     # reuse results stored by earlier builds
        IncrementalBuilder(           # skip work whose inputs haven't changed
            ..., create_graph),
        cache_dir="build/cache",
    ),
    staging_dir="build/staging",
)

This note answers one question: what do those wrappers actually do, mechanically — and what are they allowed to touch?

2. The problem: the plan grows while the build runs

The obvious reading of the spec is that each wrapper rewrites the execution plan before the build starts. That can't work, because a Brix plan isn't finished when the build starts.

An ExpandAll node is a placeholder that means "one compile per source file — whatever files there turn out to be." When those sources are generated, they don't exist until an earlier action runs. So the plan begins with just two nodes — the placeholder and the link step — and grows into its real shape during execution. A rewrite pass that runs up front would wrap those two nodes and miss every actual compile: exactly the nodes that caching and staging exist for.

So layers can't work by rewriting the plan. They have to make their decisions while the build is running, one node at a time.

3. The ground rules

Before saying what layers do, pin down what nobody may do. Three rules, enforced by one owner — the scheduler:

  1. The plan only grows. Nodes and edges get added, never removed, replaced, or rewired. All additions go through the scheduler's one insertion channel.
  2. A node never changes. Once inserted, its definition — action, command, declared inputs and outputs — is frozen. Anything that varies at run time (status, result) lives in a table the scheduler owns, not in the node.
  3. Status only moves forward. pending → running → done, failed, or skipped. Never backwards, never twice.

A node is like a promise: fixed identity, a value that gets filled in exactly once. Two things look like they break rule 2, and don't:

  • Expansion. When ExpandAll runs, it doesn't get replaced by its children. It stays in the plan, marked done, and the scheduler appends the concrete compile nodes next to it. Nothing that existed before is different after — the plan just knows more.
  • Realization. A collection like build/generated/{name}.cpp is one thing: the set, whatever its members turn out to be. When it realizes, its membership goes from unknown to known: {foo, bar}. That's a value being filled in, not a node being swapped out. And the collection has to keep existing after realization, because it's the thing the incremental layer attaches membership history to — "last build it was {foo, bar, baz}, now it's {foo, bar}" is a comparison on the collection across builds (§8).

Even "skipping" a node needs no special machinery. Every shortcut a layer offers turns out to be the same move: finish the node with a result that came from somewhere other than running a process.

4. How a layer plugs in

Each layer is an object with four hooks: 

class BuildLayer:
    def on_build_begin(self, plan, ctx): ...
        # atomic: set up the staging dir, or recover from an interrupted build

    def around_node(self, node, ctx, inner) -> ProcessResult:
        # gets a chance to answer for the node without calling inner(),
        # or to adjust ctx before passing the call inward
        return inner(ctx)

    def on_collection_realized(self, expand_node, members, ctx): ...
        # membership is now known — compare against last build, propose cleanup

    def on_build_end(self, result, ctx): ...
        # atomic: everything succeeded -> commit staged files; else leave them

The important hook is around_node. When a node becomes ready, the scheduler does not call the process directly. It wraps the process call in each layer's around_node, innermost first, and calls the outermost: 

# executor, when a node becomes ready:
call = lambda ctx: run_process_node(node, ctx)
for layer in [incremental, cache, atomic]:   # innermost first
    call = wrap(layer.around_node, node, call)
result = call(ctx)                           # scheduler records done/failed as today

The wrapping order is exactly the builder nesting from §1 — the same composition, applied per node at run time instead of once up front. That's what fixes Figure 1: a node created mid-build gets the identical stack the moment it becomes ready, because the stack is applied when nodes run, not when the plan is made.

Two couplings are deliberate here, not accidental. First, the cache key and the incremental fingerprint are computed from the same facts — command template, tool identity, input content hashes — so they should share one fingerprint function rather than drift apart. Second, because atomic is the outermost layer, outputs restored from the cache land in staging exactly like outputs written by a process. The spec's requirement falls out of stack order for free, with no special case.

7. Where the bytes live

Each layer owns one piece of storage, and nothing else may touch it. The workspace — the user's actual files — is written by exactly one arrow in this whole picture: the atomic commit, which only happens if every node succeeded.

This picture is also the crash-safety argument. If the build dies at any point, the workspace still holds the previous good state, staging holds a partial build you can inspect or resume (on_build_begin looks for it), and the metadata store was only updated in step with what actually happened — so the next build's freshness checks tell the truth.

8. Work that layers add: cleanup

Most of a layer's job fits in around_node. Two things don't, because they aren't decisions about a single node:

A source file was deleted

Say src/baz.cpp existed last build and is gone now. No fingerprint check will ever notice — there's no node to check. The incremental layer catches it in on_collection_realized: when the collection's membership becomes known, compare it to last build's membership. baz vanished, so build/obj/baz.o is stale and must go, and the link must rerun.

The deletion is real work, so it becomes a real node: the layer proposes it, the scheduler inserts and wires it — the same channel expansion uses. Being a node buys it everything nodes get:

  • Ordering — an edge from the deletion to the link means the link can never see the stale baz.o.
  • Staging — the atomic layer wraps deletion nodes like any other, so the "delete" is staged and only committed with the rest of the build.
  • Visibility — dry-run and status can list planned deletions, because they're in the plan.
  • Failure handling — a deletion that fails produces a normal result and cascades like anything else.

An action failed and left junk behind

Deleting the half-written outputs of a failed action is also node-shaped work, with one twist: it must run because its trigger failed — and normal readiness forbids that, since failure skips successors. The fix is a property of the edge, not a bypass of the rules: an edge has a trigger mode. on-success is the default and works exactly like today. on-completion fires whether the source succeeded or failed. Failure-cleanup nodes hang off their action with an on-completion edge; every ordinary edge keeps today's behavior.

9. Logical addresses, physical places

A node declares that it writes build/obj/foo.o. With the atomic layer on, the file actually gets written under build/staging/…. Doesn't that mean the layer changed the node's outputs — breaking rule 2?

No, and the distinction matters. build/obj/foo.o is the node's logical address: it's what dependency inference ran on, what the cache key hashes, and what membership diffs compare across builds. Rewrite it and the node's identity forks mid-build. So the node keeps its logical address forever, and the mapping to a physical place happens at the last moment — when the command is rendered — using the context: 

class NodeContext:
    workspace_root: Path   # where inputs are read and collections realize
    output_root: Path      # where declared outputs get written
                           #   normally: the workspace
                           #   under atomic: the staging dir
    # later: env, scratch dirs, per-node metadata handles

The atomic layer just points output_root at staging. The compile writes there; the downstream link, rendered under the same context, reads from there; the commit at the end moves everything into place. No node ever knew. Think mount namespace, not sed: the addresses in the program never change — the layer changes what they're mounted onto.

The context is also deliberately small and plain-data. It's the one sanctioned way a layer reaches inside a node's execution, and it crosses the future Rust FFI boundary as-is.

10. Build order

The plan is to land this in five steps, each one proving the previous seams before adding risk:

StepWhatWhat it proves
1Add BuildLayer, NodeContext, and the stack to the executor. CleanBuilder runs with an empty stack.The seams exist and change nothing — full test suite stays green.
2A trivial layer: logging or dry-run.Composition works, including for runtime-expanded nodes — the cheapest possible proof.
3Persistent metadata + change detection; IncrementalBuilder.Fingerprints, membership history, deleted-source and failed-output cleanup — the correctness core.
4CacheBuilder, sharing the fingerprint function.Result restore and failure replay through the same seam.
5AtomicBuilder: staging via ctx.output_root, commit in on_build_end.The most invasive capability lands last, on proven seams.

11. The rules, restated

  • The logical graph is clean-build truth — layers never touch what the user declared; they intercept execution.
  • Nodes are effectively immutable — the plan only grows, status only advances, definitions never change. Expansion refines, realization resolves, and atomic remaps logical paths at render time; none of them rewrite a node.
  • Builder nesting is the layer order — the user's composition and the runtime stack are the same thing.
  • Every shortcut is a result obtained elsewhere — up-to-date, cache hit, or process run all end in a ProcessResult; downstream can't tell the difference.
  • Cleanup is not user-authored — stale and failed-output deletions are layer-proposed nodes, inserted at run time through the same channel as expansion.
  • Failed results are real results — a cached failure replays as a failure and cascades normally.
  • Cache and atomic don't know about each other — stack order alone routes restored outputs through staging.
  • Rust eventually owns the engine — scheduler, stack dispatch, fingerprints, metadata, and NodeContext all live below the DSL boundary; layers are engine policy, not build-file features.
