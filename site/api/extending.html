    Extending brix¶

    Brix has three plug-in seams. Each is an injected object you pass to a builder, so a project can swap in its own behavior without touching the engine.

    Change detection¶

    How Brix decides whether a file changed. The default stats and hashes on demand; GitChangeDetector accelerates a git working tree by trusting git's own view of what is unmodified. It accelerates both engines (see docs/roadmap.md).

    Brix's supported Python authoring and extension API.

    Engine implementation types live in their defining modules and are not part of the top-level v1 contract. See docs/python-api.md.

    GitChangeDetector ¶

    GitChangeDetector(root='.', metadata=None, inner=None)

    Wraps a TimeAndHashChangeDetector, vouching tracked+unmodified files as unchanged without stat-ing them. Presents the same interface (the incremental and cache layers use it identically), sharing the inner detector's metadata.

    Configuring this detector accelerates both engines: the Python engine uses this class directly, and on the Rust engine the builder emits a git_detection flag (see builders.py) that turns on the native mirror in rust/brix-core/src/gitdetect.rs — same vouch, same baseline/dirty metadata, so a build started on one engine continues correctly on the other.

    changed_paths ¶

    changed_paths()

    Absolute paths changed since the last build — the working-tree diff, commits since the baseline, and the last build's dirty set (a file dirty then and clean now was reverted, which is still a change since that build). None when git cannot answer (no repo, no baseline, a git call failed): callers must treat None as "anything may have changed".

    This is the enumeration query the lazy-loading tier uses to decide which packages to load, independent of any loaded graph.

    Result caching¶

    Where built results are stored so they can be restored — across workspaces or across a team. Implement CacheStoreProtocol to back the cache with your own storage.

    Brix's supported Python authoring and extension API.

    Engine implementation types live in their defining modules and are not part of the top-level v1 contract. See docs/python-api.md.

    CacheStore ¶

    CacheStore(directory)

    Content-addressed result store under one directory.

    restore ¶

    restore(fingerprint, entry, ctx)

    Copy the entry's outputs to ctx.output_root. False (and no further copies) if the entry is corrupt — the caller falls back to running the process, which overwrites anything partial.

    CacheStoreProtocol ¶

    Bases: Protocol

    What CacheLayer requires of a store. Structural — a store need not subclass this, only match the three methods.

    An entry is an opaque dict a store returns from load and receives back in restore; the layer only reads entry["result"] (a ProcessResult as a dict) from it. Everything else in the entry is the store's private business. restore copies the entry's cached outputs to ctx.output_root and returns whether it fully succeeded; a store may let I/O errors propagate — the layer catches them.

    HttpCacheStore ¶

    HttpCacheStore(
    base_url, *, auth=None, retries=2, timeout=30.0
)

    Content-addressed result store backed by an HTTP GET/PUT endpoint.

    restore ¶

    restore(fingerprint, entry, ctx)

    Fetch every blob first, then write — so a missing/failed blob is a clean miss (False) with no partial outputs left behind, matching the local store.

    store ¶

    store(fingerprint, result, outputs)

    Upload blobs, then the entry last — so an entry is only ever visible once all its blobs are (a partial upload reads back as a miss).

    TwoTierCacheStore ¶

    TwoTierCacheStore(front, back)

    A fast local store in front of a slower shared one.

    A read checks the front first, so a local hit costs no round-trip to the back (typically a remote/team cache). A back hit is served and then promoted into the front, so the next build on this machine hits locally. A write populates the front and best-effort the back — a write to an unreachable back never blocks local caching.

    Both tiers must share the entry shape used here: entry["result"] (a ProcessResult dict) and entry["outputs"] (an iterable of the logical output paths). The built-in CacheStore satisfies this; so does any store modeled on it. Promotion never touches a tier's internal blob layout — it re-stores from the files restore just wrote — so the two tiers need not share physical storage, only that entry shape.

    DepSet dataclass ¶

    DepSet(artifacts=(), compile_flags=(), link_flags=())

    An ordered set of resolved artifact paths (jars, .a/.so) plus the flags they require. Both flag tuples are empty for a JVM classpath (the classpath is the artifacts); C++ adapters populate compile_flags (-I/-D) and link_flags (-L/-l) — separate because a -I belongs on the compile and a -l on the link.

    files ¶

    files()

    The artifacts as byte-lens file atoms (the consumer re-lenses).

    Content lenses¶

    How Brix judges whether a change actually matters to dependents — comparing a file by meaning, not bytes. Register a ContentIdentity to add your own lens; the built-in jvm-abi, kotlin-abi, and ts-dts lenses are selected by the typed helpers (java.abi, kotlin.abi, ts.dts).

    Content-identity plugins: fingerprint a file by meaning, not bytes.

    A ContentIdentity turns a file's bytes into a digest of some semantic identity — e.g. jvm-abi hashes a jar's API surface, not its bytes — so a dependent's fingerprint changes only when the meaning it depends on changes. This is the Python reference engine's lens computation; the lens is selected by an atom's content_key (set by a typed subclass like brix.java.AbiFile — the author writes java.abi(expr), never the name). It is opt-in per atom; the default is byte hashing. It affects fingerprint material only: what is stored, staged, restored, and compared for output-intactness still uses bytes (see docs/java-fast-builds.md and docs/content-key.md).

    The versioned tag <name>@<version> is part of the fingerprint payload, so bumping a plugin's version cleanly invalidates everything it fingerprinted. Bump it on any change to extraction or normalization.

    The built-ins (jvm-abi, ts-dts) are also implemented in the Rust core (rust/brix-core/src/identity.rs) so every skin gets them; the digests are cross-engine cache keys, so the Python code here remains the reference implementation, and a version bump in one implementation must land in both. A custom plugin registered here crosses the boundary as the content_identity extension trait: the engine calls its digest back per file (from build worker threads), and its digests cache in metadata.json under the same versioned tag either engine would use.

    ContentIdentity ¶

    Bases: Protocol

    A registered content-identity plugin.

    digest ¶

    digest(path)

    The identity digest of the file. Raises on a file it cannot interpret (the engine falls back to byte hashing under a :raw tag).

    JvmAbiIdentity ¶

    Java ABI hashing: a dependent recompiles on API changes, not on implementation-only changes. Delegates to the pure-Python parser in brix.jvmabi.

    KotlinAbiIdentity ¶

    Kotlin ABI hashing: jvm-abi semantics, except classes whose Kotlin metadata declares inline functions/accessors (whose implementation — bodies, line tables, nested synthetics — compiles into consumers) count by whole-class bytes. Delegates to the pure-Python parser in brix.kotlinabi.

    TsDtsIdentity ¶

    TypeScript declaration (.d.ts) hashing: a consumer recompiles on an API-surface change, not on an implementation-only change or a doc-comment edit. Delegates to the pure-Python normalizer in brix.tsdts.

    register ¶

    register(identity)

    Register a plugin under its name (replacing any existing one).

    get ¶

    get(name)

    Resolve a name to its plugin. Unknown names are loud — a typo in identity= must not silently degrade to byte hashing.

    tag ¶

    tag(identity)

    The versioned fingerprint tag, e.g. jvm-abi@1.

    builtins ¶

    builtins()

    The content-identity names the core builds in, as opposed to custom skin plugins registered later. A graph's content keys outside this set cross the engine boundary as content_identity digest callbacks.
