    Java¶

    Typed Java actions — compilation through a warm javac worker, jar assembly, JUnit test runs — with the jvm-abi lens (abi) so a dependent recompiles only when an upstream module's public API changes, and resolver adapters (pom, maven, gradle) that adopt an existing build's classpath.

    Typed Java actions.

    Like brix.cpp, these lower into the generic action/data model when added to a graph — one underlying representation, so C++, Java, and raw process actions compose freely (a C++ tool can generate Java sources that feed a JarAction).

    java.JarAction(
    source_files=(
        data.glob("src/main/java/{class_name}.java")
        + data.glob("build/generated/java/{class_name}.java")
    ),
    output_file=data.file("build/libs/app.jar"),
    entry_point="App",
)

    Java compilation is inherently whole-program (javac sees every source at once), so this lowers to two actions: one javac invocation producing a classes directory, and one jar invocation packaging it.

    Directory convention: the classes directory is declared as a data.file output of the javac step (so it renders through output_root and stages under atomic builds) and as a data.file input of the jar step (so it resolves through the overlay). Class-file tracking uses a bare {name}.class glob, which is recursive by default (matches across /) and so covers packaged classes (com/foo/Bar.class), not just default-package ones — a changed packaged class thus re-runs the jar step, avoiding a stale jar.

    AbiFile ¶

    AbiFile(path)

    Bases: FileData

    A jar/class compared through the JVM ABI lens, not its bytes: a dependent recompiles on an API change, not an implementation-only one. brix.java owns this lens — the core dispatches the jvm-abi name through its content-key registry (docs/content-key.md).

    AbiGlob ¶

    AbiGlob(pattern, exclude=())

    Bases: GlobData

    The glob counterpart of AbiFile: the JVM ABI lens applied to every matched jar/class.

    JarAction ¶

    JarAction(
    *,
    source_files,
    output_file,
    javac=None,
    jar_tool=None,
    options=None,
    classes_dir="build/classes",
    entry_point=None,
    classpath=None,
    processorpath=None,
    resource_dir=None,
    javac_worker=None
)

    Bases: Action

    Compile Java sources and package them into a jar.

    processorpath contains annotation-processor jars. Unlike classpath, these are tracked by their complete bytes: changing processor implementation must recompile sources even when the processor's Java ABI did not change.

    JUnitTestAction ¶

    JUnitTestAction(
    *,
    test_sources,
    classpath,
    console_jar,
    javac_worker,
    name="junit tests",
    test_classes_dir="build/test-classes",
    test_resource_dirs=None,
    java=None,
    options=None,
    select="--scan-class-path"
)

    Bases: Action

    Compile JUnit 5 test sources and run them with the platform console launcher, so brix runs a suite only when its inputs actually change.

    The key move is two lenses on the same classpath jars: the test compile depends on them through jvm-abi (compilation cares only about the API), while the test run depends on them through their bytes (execution cares about the implementation). So an implementation-only change to the code under test does not recompile the tests but does re-run them; a change touching nothing on a suite's classpath re-runs nothing.

    The run declares no file outputs, so it replays purely on its input fingerprint: a passing suite is cached like any result (and restored on a clean checkout), while a failing suite is recorded as failed and re-runs until its inputs change.

    classpath is the code under test (jars). console_jar is a junit-platform-console-standalone jar — the runner and the source of the Jupiter API the tests compile against. Tests compile through the warm javac worker (required, for the classpath join).

    pom ¶

    pom(
    path,
    *,
    mvn="mvn",
    scope="compile",
    cache_dir=".brix-deps",
    cwd=None
)

    Adopt an existing Maven pom.xml: resolve its declared dependencies to a classpath and return it as a DepSet. The dependency declarations stay in the pom — this is the migration path (point brix at what Maven already resolves). Editing the pom re-resolves (the cache key is the pom's bytes). cwd is where Maven runs (pass the project dir when mvn is a ./mvnw wrapper); mvn may be a wrapper path like "./mvnw".

    maven ¶

    maven(
    coords,
    *,
    mvn="mvn",
    scope="compile",
    cache_dir=".brix-deps",
    cwd=None
)

    Resolve inline Maven coordinates ("group:artifact:version") to a classpath via Maven, returned as a DepSet. The declarations live in brix.py — the greenfield / single-file path. Editing the list re-resolves. Naming the engine (maven) is deliberate: Maven and Gradle apply different version-conflict rules, so this gives Maven's resolution.

    gradle ¶

    gradle(
    path,
    *,
    gradle="gradle",
    configuration="compileClasspath",
    project=None,
    cache_dir=".brix-deps",
    cwd=None
)

    Adopt an existing Gradle project: resolve a configuration's classpath (Gradle's compileClasspath / runtimeClasspath / testRuntimeClasspath, the analog of a Maven scope) and return it as a DepSet. This is the migration path for a Gradle build — the declarations stay in the build files; brix drives Gradle and consumes what it resolves (with Gradle's own version-conflict rules). Editing a build file re-resolves (see _GRADLE_MANIFEST_FILES for exactly which files the cache key covers).

    path is the project directory (or a build script inside it). project is a Gradle project path (":service-a") to target a subproject of a multi-project build; None targets the root project. gradle may be a wrapper path like "./gradlew"; cwd is where it runs (defaults to the project dir).

    abi ¶

    abi(expr)

    View a data expression through the JVM ABI lens: every plain file/glob atom becomes its AbiFile/AbiGlob counterpart, so fingerprints compare those files by API surface. Non-file atoms (tools, values) and atoms that already carry a lens pass through unchanged. A classpath is many jars, so this applies across an expression's atoms, not just one file.

    javac_worker ¶

    javac_worker(
    graph,
    *,
    java=None,
    javac=None,
    jar_tool=None,
    work_dir="build/.brix-java"
)

    Add the javac worker bootstrap to graph and return its WorkerSpec.

    The worker is a small in-process JavaCompiler wrapper shipped with brix; it is compiled and jarred by two plain (spawned) nodes here, so the worker jar is itself a fingerprinted, cacheable build product. Pass the returned spec to JarAction(javac_worker=...) to route module compilation through the warm worker.

    Idempotent: called more than once on a graph, it adds the bootstrap only once and returns the same spec, so many JarActions share one worker jar.
