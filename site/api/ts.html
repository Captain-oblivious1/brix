    TypeScript¶

    Typed TypeScript actions built on tsc, with the ts-dts lens (dts) so a dependent recompiles only on a public-declaration change, plus automatic import tracking (a --listFiles depfile) so editing a source a module imports — even outside its own tree — re-stales it. TypedocAction runs typedoc over a project's own sources as a tracked, incremental step.

    Typed TypeScript actions.

    Like brix.java and brix.cpp, these lower into the generic action/data model when added to a graph — one underlying representation, so TypeScript composes freely with the other languages (a code generator can emit .ts that feeds a ts.CompileAction; a .js bundle can feed a later step).

    ts.CompileAction(
    sources=data.glob("src/{name}.ts"),
    out_dir="dist",
    options=["--module", "nodenext", "--target", "es2022", "--strict"],
)

    tsc compiles a set of .ts sources into an outDir of .js (and, with declaration emit, .d.ts). The action declares the sources as inputs and the emitted .js/.d.ts as recursive {name} globs under out_dir (bare {name} matches across /, so nested modules — sub/mod.js — are tracked, not just top-level ones), so brix owns incrementality: it re-runs tsc only when a source or a tracked dependency actually changes, rather than delegating to tsc --build's own up-to-date check.

    The cross-module lens. A module that type-checks against another module's built declarations declares them via dependencies= — the emitted upstream .d.ts files, viewed through the ts-dts lens (brix.ts owns this typed atom, as brix.java owns AbiFile). Because tsc's declaration emit writes only the public API, an implementation-only change upstream produces a byte-identical .d.ts and the ts-dts fingerprint is unchanged, so the dependent replays instead of recompiling — the TypeScript counterpart of the jvm-abi shortcut (docs/content-key.md). The upstream .d.ts are tracked fingerprint inputs; tsc's own module resolution locates them on disk (they sit in the upstream out_dir the dependent imports from), so no classpath-style flag is needed.

    Automatic import tracking. The declared sources glob covers a module's own tree, but a TS import can reach a shared .ts outside it (a common utils/ file, an ambient .d.ts). Left undiscovered, editing that file would leave the module stale — the TS version of the C/C++ header problem. So by default (track_imports=True) brix wraps tsc in a --listFiles recorder that writes a Makefile depfile of every workspace .ts/.d.ts the compile actually read; the incremental layer scans it exactly like a cc -MMD one, so editing a deeply-imported source re-stales the compile. It is complementary to dependencies=: a declared upstream .d.ts is tracked through the ts-dts lens (impl-only upstream change → replay), and its directory is excluded from the depfile so that byte-tracking never overrides the lens; the depfile is only for the undeclared source imports the lens doesn't cover. Set track_imports=False for a bare single tsc spawn.

    Scope for now: no warm compiler daemon (like brix.cpp, unlike brix.java's javac worker) and no npm/node_modules resolver (that is the ts.npm-style adapter of docs/dependencies.md, still planned). tsc is often not global; pass tsc=data.tool(".../node_modules/.bin/tsc") to point at a local install.

    DtsFile ¶

    DtsFile(path)

    Bases: FileData

    A .d.ts declaration file compared through the ts-dts lens, not its bytes: a consumer recompiles on a public-API change, not an implementation-only change or a doc-comment edit. brix.ts owns this lens — the core dispatches the ts-dts name through its content-key registry (docs/content-key.md).

    DtsGlob ¶

    DtsGlob(pattern, exclude=())

    Bases: GlobData

    The glob counterpart of DtsFile: the ts-dts lens applied to every matched .d.ts.

    CompileAction ¶

    CompileAction(
    *,
    sources,
    out_dir,
    tsc=None,
    options=None,
    declaration=True,
    dependencies=None,
    track_imports=True,
    python=None
)

    Bases: Action

    Compile a module's TypeScript sources with tsc into out_dir.

    Emits .js for every source and, when declaration is set (the default, so the module is usable as a dependency), a .d.ts beside each. dependencies is the list of upstream modules' built .d.ts this module type-checks against; they are tracked through the ts-dts lens, so an implementation-only change upstream lets this module replay.

    TypedocAction ¶

    TypedocAction(
    *, entry_points, output_dir, typedoc=None, options=None
)

    Bases: Action

    Generate HTML API docs for a project's own TypeScript sources with typedoc.

    Documentation of the user's code, run as an ordinary tracked step: the declared entry_points (the sources) are inputs, so the doc set rebuilds on a source change and replays when nothing changed. Pass typedoc flags (--name, --excludePrivate, --tsconfig …) through options.

    typedoc is usually a local install, not global; pass typedoc=data.tool(".../node_modules/.bin/typedoc") to point at it.

    ::

    ts.TypedocAction(
    entry_points=data.glob("src/{name}.ts"),
    output_dir="build/docs/api",
)

    dts ¶

    dts(expr)

    View a data expression through the ts-dts lens: every plain file/glob atom becomes its DtsFile/DtsGlob counterpart, so fingerprints compare those declaration files by public surface. Non-file atoms (tools, values) and atoms that already carry a lens pass through unchanged. A module can depend on many upstream .d.ts, so this applies across an expression's atoms.
